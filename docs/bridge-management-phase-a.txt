WhatsApp Management — Phase A
=============================

Scope
-----
Read-only diagnostics inside /support. No Node lifecycle/transport/storage
changes, migrations, recovery executors, or new customer-message access.
Existing Super Admin pairing and removal remain in their separate dialog.
The existing removal/decommission mechanisms are unchanged by this release.

Open the dashboard WhatsApp button as Admin or Super Admin. Select an identity
to inspect connection, authentication, storage, transport/heartbeat and delivery
evidence independently. The inventory includes disabled and quarantined lines.
Bridge uncertainty counts are bridge evidence counts, not a database-wide count
of UNCERTAIN customer messages. No delivery is resent or reconciled here.

Read-only API (prefix /api/support/whatsapp-linked-device)
-------------------------------------------------------
GET /management                         Admin / Super Admin
GET /lines/{id}/diagnostics              Admin / Super Admin
GET /lines/{id}/history                  Admin / Super Admin
GET /lines/{id}/auth-recovery            Super Admin only

No QR, credentials, private paths, customer contents or raw provider exceptions
are included in these responses. The bridge's existing private status and
assessment endpoints are the only bridge calls. No filesystem/journal scans.
Metadata comes from SELECT-only repository methods, never list_payload/seeding.
Reads neither authorize recovery nor make an identity eligible for sending.

Authorization changes
---------------------
Stored roles stay admin=Admin, supervisor=Super Admin, agent=regular staff.
Three explicit SupportAgent capabilities govern management reads, connection
changes and detailed authentication assessment. Existing broad is_supervisor
semantics remain unchanged for other Customer Support features.

Super Admin only: legacy linked-device registration, connect, disconnect,
DELETE (unlink and decommission), registry enable/disable, rename, Meta sync,
saved-number removal and historical relink management. The service checks also
protect direct callers. Mutations retain existing CSRF requirements.
The legacy linked-device status endpoint still permits ordinary staff status,
but returns QR data only to Super Admin. New management endpoints never return QR.
Ordinary outage/composer health and conversation/media authorization are unchanged.

Freshness and limitations
------------------------
The visible management view refreshes about every five seconds through the
existing dashboard coordinator, which pauses when the tab is hidden. Per-worker
single-flight observations are cached for five seconds; metadata/history for
thirty seconds; authentication assessment for five seconds. Responses are no-store.
Unknown values remain null/unknown, never synthesized healthy/zero. Failed
requests mark retained browser observations stale. Heartbeat age is separate
from HTTP observation time; samples older than 120 seconds are labeled stale.

Recent incidents include first observed nonconnected states and subsequent
state/category/lifecycle/storage changes while this API worker is observed.
They are bounded in memory, not a durable incident ledger; restarts, multiple
workers and observation gaps can omit events. Existing saved registry audit
history is available per identity, latest thirty records. Free-text details are
excluded. There is no new persisted incident database in Phase A.
Offline journal proof remains a separate operator prerequisite. An assessment
always reports recovery_allowed=false, including complete evidence. Quarantined
credentials cannot be reused. Authentication operation details are bounded to
100 entries with an explicit total/truncation indicator.

Verification and production-only workflow
----------------------------------------
The user authorized focused local checks with mocks and isolated data. Do not
access DEV. Implement locally, commit, push, review a PR, then obtain explicit
approval before production deployment. Never use production credentials in tests
or send customer messages. See bridge-management-production.txt for the review
results, live read-only observations, activation gates and rollback procedure.

1. Sign in separately as regular staff, Admin and Super Admin. Regular staff
   retain normal tickets, media and outage status. Only the two manager roles
   see management; only Super Admin sees authentication assessment and the
   existing pairing/removal entry. Capture screenshots at desktop/mobile widths.
2. With real session cookies and valid CSRF, confirm staff/Admin receive 403 for
   POST linked-device /lines, /connect, /disconnect, DELETE /lines/{id} in both
   modes; registry PUT state/name, DELETE number and POST account sync. Check
   no provider call or registry mutation occurred. Verify regular staff receive
   403 on all four new routes; Admin receives 403 on auth-recovery.
3. Check connected, reconnecting, logged-out, disabled, fenced and quarantined
   mocked identities. Names/phones, IPv4/IPv6, last heartbeat, disconnect reason,
   retry scheduling, storage issues, pending callbacks and uncertainty agree
   with the mock source. Disabled and quarantined lines never become sendable.
4. Interrupt only the mock status source. Confirm inventory remains visible,
   state becomes unknown, previous observation age is clear and no zero/healthy
   state is invented. Test missing diagnostic fields, stale heartbeats, registry
   outage and individual missing identities. Restore telemetry and refresh.
5. Inspect all management responses and logs with synthetic sensitive canaries
   in raw QR, auth, errors, audit details and message fields. Canaries must not
   appear. QR remains available only in the existing Super Admin pairing view.
6. Switch selections while requests are pending, close/reopen the dialog, sign
   out during a pending read, and change roles. Old responses must not repopulate
   another selection/session. Repeated polls preserve focused identity buttons.
7. Observe the network for approximately five-second polling, no duplicate
   concurrent reads, thirty-second history refresh and zero mutation requests
   from the new controls. Every future recovery button remains disabled.
8. Check incident observation limits and saved operator history. Decommissioned
   lines must distinguish confirmed remote unlink from unconfirmed local removal.
   Inspect technical blocker codes as Super Admin without clearing any fence.

Focused automated checks, separately (historical unit modules install dependency
doubles). Run from an isolated directory without .env and with an explicit
PYTHONPATH to the repository; use absolute test paths where necessary:
  venv/bin/python -m pytest -q tests/test_bridge_management.py
  venv/bin/python -m pytest -q tests/test_linked_device_api.py
  venv/bin/python -m pytest -q tests/test_whatsapp_number_registry.py
  venv/bin/python -m pytest -q tests/test_bridge_management_release.py
  SUPPORT_TEST_BROWSER=chromium venv/bin/python -m pytest -q tests/test_bridge_management_browser.py
  node tests/bridge_management_ui.test.cjs
  venv/bin/python scripts/check_support_assets.py
Local review: parse changed Python files and git diff --check. No full suite or
unrelated build is needed. Existing authenticated reads may update the staff
session last_seen timestamp; management never writes WhatsApp/customer state.

Phase B remains separate: safe reconnect, durable pause/resume and deferred
work, operation journal/idempotency, per-identity lifecycle locking, action rate
limits, complete outcome audit, durable incident capture and failure rehearsal.
Do not reinterpret /connect as safe reconnect or /disconnect as pause.
