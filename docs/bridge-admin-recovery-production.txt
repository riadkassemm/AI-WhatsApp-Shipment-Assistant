=========================================

No DEV access. No production mutation, callback replay, service restart,

Activation boundary
-------------------
WHATSAPP_ADMIN_RECOVERY_ENABLED defaults to false in BOTH API and bridge.
With it false, new commands are unavailable and no recovery worker starts.
An already durable bridge pause is still honored. Do not use the flag to clear
holds or to downgrade a running Phase B installation with outstanding work.
The API refuses enabled startup if required tables, columns or unique keys are
missing. Management GETs only read cached monitoring and bounded SQL metadata;
they do not call registry seeding, provider operations or storage maintenance.

This release contains Node changes and an additive SQL migration. Activating
it requires an expressly approved graceful bridge transition. It cannot keep the
eligible identities' sockets open across replacement of their owning process.
No logout, relink, credential reset, journal rewrite or duplicate owner is needed.
The expected outcome is reconnection of exactly the identities that were eligible
and connected in the fresh preflight snapshot, with reused credentials over IPv4.
The identity set is NOT fixed: Super Admins add and remove numbers. Every gate
compares against a snapshot taken in the same window, never a remembered list.
PR #90 (callback fix) is merged and deployed; it is in this branch's ancestry.

Behavior and ownership
----------------------
- Admin (stored role admin) and Super Admin (supervisor) receive the explicit
  can_recover_whatsapp capability. Staff has none. Existing Super Admin pairing,
  rename/removal and privileged authentication-assessment boundaries stay intact.
  No role obtains additional conversation or attachment access.
- Public API prefix /api/support/whatsapp-linked-device:
    POST /lines/{id}/operations        create a queued command (202)
    GET  /operations/{uuid}            status and sanitized audit
    GET  /lines/{id}/operations        latest 30 commands
    POST /operations/{uuid}/cancel     queued-before-dispatch cancellation only
  Mutations require the real cookie session and CSRF token. Creation requires a
  UUID Idempotency-Key matching operation_id, confirm_line_id, action, and the
  observed bridge epoch, connection generation and administrative state version.
  Unknown parameters and force/reset actions are rejected. Role/operator values
  are derived on the server; clients cannot supply them.
- Private bridge POST/GET /v1/lines/{id}/management-operations[/{uuid}] use the
  existing shared-secret, loopback boundary. They are never public staff routes.
- SQL stores controls, commands, original operator/role/parameters/timestamps,
  outcome/reason and append-only transitions including the cancellation actor.
  One active command per identity is reserved transactionally. DB connection
  mutexes coordinate API workers; they are NOT proof of transport ownership.
  Limits: 10 new requests/operator/minute, 3/action/identity/minute, plus the
  bridge's 6/identity/minute and 3/action/identity/minute admission limits.
- The bridge's exclusive directory owner admits a command synchronously before
  yielding; existing pairing/removal and auto-reconnect cannot overlap it.
  State/journal persistence records admission before processing. UUIDs and
  versions prevent duplicate execution; the latest 128 terminal records are
  retained on the bridge and SQL retains the complete audit history.
- Reconnect requires paired reusable credentials matching committed state,
  no recovery fence, current auth/directory ownership, healthy/fresh storage,
  settled provider work, and confirmed old transport closure/event release.
  It uses paired-only socket creation, rejects QR challenges, never calls reset,
  and reports success only after the provider reports a ready connection.
- Pause does not close a healthy socket. SQL immediately stops API admission;
  the bridge durably suppresses new sends and automatic reconnect. Already
  dispatched work, receipts, callbacks and accepted auth writes can complete.
  Stored credentials, deduplication and unknown-delivery records are retained.
- Resume revalidates before and after persistence. Failed validation leaves the
  number paused. A resume interrupted by a bridge restart (even after saving
  paused=false) restarts PAUSED and is not replayed. Disconnected eligible
  sessions use the existing reconnect scheduler after resume; a resume success
  is not a claim of connection success.
- A command the bridge rejects before admission (4xx: stale epoch/version,
  ineligible, rate limited, unknown line) failed without effect; a rejected
  pause therefore restores the previous API admission state. A pause that the
  bridge admitted stays paused even if it later fails or is interrupted.
- Safe reconnect waits at most 120 s for a provider result, then reports
  CONNECTION_NOT_CONFIRMED and releases lifecycle admission.
- Retained staff work uses admin_hold, preserving offline-expiry evidence and
  existing delivery-token, assignee and conversation checks. Media is checked
  again before dispatch. Order is kept PER CONVERSATION (same ticket; for bot
  vs staff work, same customer digits on the same line), never across the whole
  line: one stuck conversation never holds other customers.
  Uncertain work (staff UNCERTAIN or bot 'uncertain') is never resent and never
  blocks later replies; it is resolved only by positive bridge evidence or the
  existing uncertain-delivery staff actions.
  A retained reply leaves admin_hold on any outcome except a proven transient
  non-send (offline/paused/storage): sent, uncertain, or an ordinary failure
  that staff may resend manually. A retained reply its sender can no longer
  send (conversation closed or transferred while paused; never handed to a
  transport) is released as an ordinary "Not sent; retry is available" reply.
  Bot replies refused by pause retain their exact text/source in a separate
  protected SQL delivery table, with stable provider idempotency IDs. The worker
  does not regenerate AI output. Revoked input is skipped. A transient non-send
  is retried after a 15 s line cooldown; a reply-specific rejection is final
  ('failed'). Unknown dispatches are only queried (at most once a minute) for
  positive confirmation, never resent. Like ordinary bot replies, retained bot
  replies are NOT mirrored into support conversations and never open tickets.
  These customer delivery rows are absent from management APIs/logs.
- If the administrative pause state cannot be read, bot replies on linked-device
  lines are refused before any provider call as a proven non-send (fail closed).
- Five-second UI refresh preserves identity/detail DOM nodes. Confirmation,
  status, disabled reasons and audit history use backend decisions. Browser
  timeouts lead to GET of the saved UUID, not another POST. Reload/new tabs can
  use durable history. Missing telemetry/pause state remains unknown.

Escalation and cancellation
--------------------------
Only a queued command whose worker mutex is free can be cancelled. Cancellation
of an undispatched pause restores its previous API admission state and records
who cancelled it. A running or unconfirmed command cannot be cancelled.
A potentially dispatched command (lost HTTP response, API restart) keeps the
identity's active-operation reservation and stays running. The worker queries
its saved UUID; only when the owning bridge answers OPERATION_NOT_FOUND does it
resubmit the byte-identical command under the SAME UUID. The bridge returns the
existing record (durable or in-flight) for a known UUID and rejects a changed
epoch (restart), connection generation or administrative version, so a
resubmission can neither execute twice nor execute late. Never submit under a
new UUID, force-close a transport, treat a Redis TTL as ownership proof, or
reset auth. Rows already in 'unconfirmed' are resolved the same way.
If a command stays non-terminal, escalate with operation UUID, line ID, reason
code and sanitized observation time; do not clear the reservation by hand.
The dashboard keeps a per-tab marker of its own submission; only a persistent
404 for that UUID more than 60 s after submission (never saved) releases it.
Incomplete/corrupt administrative state also blocks activation.

GO / NO-GO gates
----------------
GO only if ALL hold; any NO-GO keeps ingress closed and the previous API serving
(the migration may stay: it is additive and ignored by older code).
  G1 PR reviewed; exact SHA approved; PR #90 ancestor; isolated 10.11 integration
     and bridge suites pass for that SHA (baseline UI fixtures documented).
  G2 Inventory S0 consistent (see above); identity changes frozen.
  G3 Fresh verified backup of DB/Redis/media + retained evidence in the record.
  G4 Migration applied; grants present; schema check passes with flag enabled.
  G5 API and bridge drained and stopped gracefully (no kill, no owner left).
  G6 S1 == S0 membership; all S0-active identities reconnected with reused
     credentials; decommissioned evidence unchanged; no QR/logout/relink.
  G7 No new dead letters, uncertain sends, auth/storage criticals or API 5xx.
  G8 Flag-on API healthy; management view correct; acceptance passed.
NO-GO examples: an S0-active identity fails to reconnect within the bound; any
identity shows QR/logout; a removed ID reappears; registry/bridge mismatch;
storage critical on an active identity; schema/grant check fails; drain cannot
be proven. Never relink, reset credentials, clear pause/hold records or replay
callbacks to pass a gate.

Rollback limitations
--------------------
Do not restore old database/Redis/media/auth/journal snapshots over new writes.
Keep the additive schema. API-only rollback may retain the new paused-aware
bridge, but an older API does not understand held bot replies or operations.
Before any downgrade, require no queued/running/unconfirmed management commands,
no administrative pause on either side, and no queued/dispatching/uncertain bot
replies or active held staff work. Never clear those records to pass this gate.
If the gate cannot be met safely, keep ingress closed and request a reviewed
forward fix; do not downgrade to code that ignores durable pause state. Any Node
rollback needs its own graceful ownership/integrity validation and explicit
approval. An API rollback must retain PR #90 and the Phase A RBAC correction.
