Permanent local decommission and bridge-only IPv4 activation
==========================================================
Supersedes the restart blocker in bridge-fenced-identity-isolation.txt and the
obsolete identity/release assumptions in bridge-ipv4-deployment.txt. Execute
only within explicit production authorization. No DEV, forced kill, hot patch,
credential recovery, uncertain resend, DNS change or server-wide IP change.

Semantics and review
--------------------
Normal unlink still confirms WhatsApp revocation. Permanent local decommission
requires proven cessation, not reusable credentials. A private atomic record in
lines.json/quarantined_lines makes the selected ID permanently ineligible.
Authentication and message-state files are fingerprinted and retained in place;
no purge tombstone, callback deletion, journal flush or repair is used. New QR
linking allocates a new ID and new authentication. Old uncertain deliveries stay
visible and protected. Local removal never implies confirmed remote unlink.

The old binary cannot gain this behavior from staging files. The committed
legacy-decommission-transition.js pins its exact revision and six source hashes.
It accepts only that binary's natural exit 1, two known aggregate shutdown
errors, no additional errors, empty old cgroup, dead old PID/start identity, held
data lock, every healthy auth marker cleared, complete healthy/shared/business
replay, unchanged identity inventory and nonregressing journal sequences. The
old code drains all healthy owners and shared work before its aggregate throw.
The exact old source was rehearsed with six healthy mocked sessions and one
failed session: healthy markers cleared; failed evidence retained; natural exit
1. Historical unresolved records are preserved as incomplete/abandoned, never
claimed to be completed. Any additional failure blocks activation.

Rollback limitations
--------------------
After quarantine, b5f8e35 is NOT a safe automatic rollback binary: it cannot
interpret the quarantine ledger and could revive abandoned credentials. Retain
it for comparison, not blind activation. Roll back IPv4 using the SAME reviewed
quarantine-capable release: close ingress, authenticated shutdown-preflight,
clean bridge drain, queue checks, clean API stop, offline validate-quarantined,
restore previous transport setting only, start API then bridge, verify six lines
and immutable quarantine, then reopen ingress. After new writes, preserve current
authoritative database/Redis/media/auth state and request approval before rollback.
Never restore an old manifest, database or session snapshot; never reuse the old
credentials. Code rollback needs an independently reviewed quarantine-capable
artifact. If a healthy-store or ownership gate fails, keep ingress closed and
report the exact failure without force or automatic recovery.
