Required deployed safeguards carried into Git
- Redis reserves pending input into a persistent in-flight list before processing;
  only confirmed completion removes it. Pending claims do not expire. Abandoned
  in-flight work blocks takeover; it is not blindly replayed.
- HTTP cancellation cannot discard the detached inbound worker. Shutdown drains
  workers and retains unresolved reservations for review. The DEV API unit source
  allows 210 seconds for the 10-second ASGI plus 180-second worker drain; review
  the actual approved target unit before installation. No server unit was changed.
- Bridge liveness is available during replay, while readiness and mutations remain
  gated. Late buffered provider events admitted before retirement are preserved.
- Known pre-request transport failures are distinguished from uncertain writes;
  large media admission is bounded without changing file-size limits.

The cause of the recurring 9–10 minute heartbeat silence remains UNCONFIRMED.

Implemented behavior
1. Per-identity exponential backoff uses equal jitter, a 60-second base cap and
   250 ms spacing between nearby retry slots. A long backoff on one identity does
   not hold another identity behind it. Existing generation/ownership guards,
   auth retirement/draining, stable-connection reset and persistence fences stay.
   408/transport failures recover; 401 retains the existing genuine-logout flow.
   Repeated 515 restart-required responses also back off exponentially.
   403/auth rejection, 440/session conflict and 411/500/protocol/session errors
   stop automatic retry and require administrator review without clearing keys.
   Terminal reasons fence raw-close retries before queued persistence finishes.
2. Text bubbles still appear immediately. States distinguish local Queued,
   Submitting, server-saved Sending, and Confirmation pending. Ambiguous errors
   cause GET lookups by the original client ID, never automatic POST resubmission.
   The new endpoint restricts lookup to the authenticated sender and ticket,
   verifies current conversation access, and respects per-user message deletion.
   Explicit Retry original request first checks that same key, then requires a
   staff confirmation. It never allocates a replacement key. Existing server-side
   UNCERTAIN handling and deliberate new-copy confirmation remain unchanged.
3. One active browser text request per WhatsApp identity; at most three identities
   concurrently, 64 queued/active jobs globally and 16 per conversation. Local
   unconfirmed drafts also have 64/16 caps. Same-identity FIFO is preserved, while
   different identities can progress. Unknown persistence holds later text for that
   identity without consuming a global concurrency slot, until the original ID is
   found. Only an explicit retry of that original ID can pass the hold. Attachments
   and quick-reply batches retain their drafts and explain the hold. A rejected
   repeat cannot turn an earlier ambiguous outcome into Not sent. A full queue
   leaves the composer draft intact.
   Attachments and selected quick replies wait for their own identity's text
   barrier. Queue limits do not change upload limits or forwarding permissions.
   Request deadlines produce uncertainty, never a claim of non-delivery. Page exit
   warns about unsaved work; page-cache navigation pauses/resumes queued work.
   Logout/session changes fence unsent jobs and prevent dispatch as another user.
   This is NOT a durable browser/server outbox: forcing a tab/device closed can
   still lose work that never reached the server, after the exit warning.
4. HTTP/SSE/history merging preserves newer edit versions and monotonically
   advances delivery evidence. Global deletion is terminal and clears old media
   URLs/body/reactions. Per-user deletion tombstones survive stale responses for
   the current staff session. These tombstones clear on logout.
5. Callback enqueue wakes the existing per-line worker only after the durable
   outbox commit. Coalesced wakeups and one task per line prevent overlap; an
   enqueue racing the worker's final empty check schedules another pass. The
   existing 1-second timer, due-time/backoff, history exceptions, deduplication,
   failure retention, shutdown draining and journal checkpoints remain in place.
6. Staff feedback distinguishes Connected, Reconnecting, Temporarily unavailable,
   Storage recovery required and Relink required. Ordinary reconnects do not sound
   an alarm until the existing prolonged-outage threshold. Visible tabs poll only
   connection health on a 5-second cadence (plus request time), using a shared
   5-second server cache; the rest of the dashboard keeps its existing cadence.
   Paired devices with transient/storage errors no longer show a misleading Pair
   action. Genuine logout/QR flows remain available to authorized staff.
7. Runtime metrics add hashed identity labels, disconnect reasons/frequency,
   recovery timings, heartbeat timing, event-loop lag, callback backlog/age,
   dead letters and uncertain sends. A bounded, indexed, read-only local SQL query
   reports database PENDING/DISPATCHING/UNCERTAIN counts. Missing observers,
   malformed data and stopped collectors cannot be reported as healthy.
   Alerts include repeated short disconnects despite current connectivity,
   heartbeat/loop delays, callback backlog, new uncertainty and missing telemetry.
   Existing disk/inode/storage/checkpoint/collector alerts remain unchanged.

Manual verification (DEV only; synthetic staff/tickets and mocked identities)
A. Queue and immediate feedback
   Delay mock identity A's response. Send two texts to A and a text to B. All
   bubbles appear immediately; B progresses, A preserves FIFO. Observe at most
   three active identities and one request per identity. Fill 16 unsaved messages
   in one conversation; the next draft must stay in the composer. Repeat Send/
   Retry clicks on one client ID: at most one browser job and one durable send.
   Drop A's response before persistence is known: later A texts must wait, B must
   progress, and an attachment batch must retain its draft with an explanation.
   Resolve the original key using GET/SSE: A resumes in order. Reject an explicit
   retry while the original remains ambiguous: it must stay Confirmation pending.
   Attempt reload/logout: receive a warning; cancelling leaves the dashboard
   functional. Back/forward restoration resumes queued work. Change staff
   sessions while a job is waiting: it must never dispatch as the new staff user.
B. Ambiguity and acknowledgment correctness
   Have the mock API save a request, then drop its HTTP response. Expect
   Confirmation pending, no Not sent and no successful tick. Observe read-only
   GET /api/support/tickets/<ticket>/messages/by-client/<original-client-id>.
   Return the original saved row: it replaces the local bubble once. No extra
   POST is issued automatically. Before provider evidence, persisted PENDING or
   DISPATCHING retains a clock. Confirmed evidence alone permits a tick.
   Also drop the request before it reaches the mock server: lookup returns null,
   and does not claim non-delivery. Explicit Retry original request uses the same
   client ID. A different staff account or inaccessible ticket cannot retrieve it.
C. Out-of-order responses and deletion
   Deliver READ over SSE, then older SENT over HTTP; read status stays. Deliver an
   older content version with a newer receipt: keep the edited body and newer
   receipt. Delete for everyone, then return an old media snapshot: body, media
   URL and reactions stay absent. Delete for me, then inject a pre-delete response:
   the message stays hidden, including in previous-ticket history. Check text
   selection, audio playback and scroll behavior on desktop and mobile widths.
D. Connection recovery and diagnostics
   In mocks, emit 408 for eight identities simultaneously. Verify jittered and
   staggered attempts, one owner per identity and bounded backoff. Hold one auth
   drain: do not create a second owner. Emit 403/440/411/500 while event persistence
   is delayed: retries stop immediately and credentials remain retained. Emit
   genuine 401: the existing relink-required behavior remains distinct. Inject a
   persistence error: sending/reconnection stay fenced; no automatic session reset.
   Feed known heartbeat RTT/frame-age/timer-delay samples and event-loop stalls;
   verify isolated identity metrics, finite values and no payload/key leakage.
E. Callback durability
   Hold the outbox commit: no callback before fsync completion. Release it:
   callbacks start without waiting for the polling tick. Enqueue during an active
   callback and during its final empty check: no lost wakeup or overlapping line
   workers. Keep the original retry delay after HTTP failure; duplicates remain
   idempotent. Repeat shutdown with active callbacks and checkpoint activity:
   drains and ownership fences must retain all pending work.
F. Monitoring and attended operation
   Simulate three short disconnects within 30 minutes, ending connected: the
   repeated-disconnect warning must still fire. Stop a collector or omit a field:
   health must fail, not silently publish zero. Simulate heartbeat observer loss,
   new database uncertainty, callback age and event-loop stalls. Inspect samples
   for credentials/message content; only fixed labels, hashes, counts and timings
   are permitted. Review existing historical callback/uncertainty backlogs rather
   than deleting them or interpreting them as new failures.
   External notifications are not configured. During a later approved deployment,
   an operator must keep attended_support_monitor.py visible: healthy must be true
   and every nonempty attention list must be reviewed. Warning alerts are displayed
   even when current connectivity is healthy. This is not an external paging system.
