Code findings
-------------
whatsapp_bridge/src/bridge.js:
- restartStaleSocket blocks the line, requests socket.end and schedules recovery.
- finishRetirement defers native end while accepted provider tasks remain.
  This is necessary on a healthy transport to finish incoming callbacks safely.
- Replacement must drain/renew the old auth owner before acquiring a new one.

whatsapp_bridge/src/storage.js:
- authFacade.drain has a 20-second deadline. Timeout marks the store failed and
  retains authentication intent/failure/active evidence; renewal then fails closed.
- runProvider can abandon a rejected operation only while the store is healthy,
  recorded mutations are empty AND current credentials equal their starting value.
- Once drain times out, even a later zero-mutation rejection cannot erase the fence.
- drain_timeout and outer provider-failure evidence currently omit final creds.

Strongly supported mechanism: failed receive progress leaves admitted provider
tasks waiting for responses; controlled retirement defers native close until
those tasks settle, while auth drain expires first. The available logs do not
identify the two pipeline bodies or prove their final in-memory credentials.
Do not call this corruption, a proven disk I/O error, or a proven safe-to-clear
false positive. Do not extend timeouts merely to mask it.

Recovery prerequisites: unresolved mandatory gate
------------------------------------------------
Do NOT delete/rename any .auth-active/.auth-intent/.auth-failure marker, reset the
store.failed flag, regenerate credentials, or restore older state over newer
state. A process restart would lose remaining in-memory evidence and does not
resolve this fence. The normal clean-stop gate can also fail on this failed store.

Before any recovery mutation, an independently reviewed procedure must establish:
1. The affected generation has no transport owner and all its admitted provider
   work has settled. A disconnected status alone does not establish this.
2. Final credential/key evidence is complete and agrees with committed sequence,
   or an explicit reconciliation is justified by complete retained mutations.
   Zero mutations plus matching STARTING credentials does not meet this gate.
3. Recovery is rehearsed on a verified private copy, preserves the original
   evidence, and cannot resend any uncertain delivery or create another owner.
4. All journals, reservations, callbacks and message state remain consistent.

The current running release has no supported interface exposing the final
credential comparison or settled-provider evidence for this failed owner.
No approved, data-preserving recovery command can therefore be supplied from
the current on-disk evidence alone. Live debugger/heap capture was not attempted;
it would require separate operational review because all eight lines share the
process and captures could contain credentials and customer data.

Proposed follow-up, separate from the UI patch:
- Reproduce failed receive + pending query + retirement using mocked Baileys.
- Distinguish healthy drain from already-failed transport retirement; settle
  failed network waiters without discarding accepted callback/auth work. Preserve
  fences for any mutation or uncertain provider outcome; no forced healthy close.
- Persist private final credential evidence and pending-work/sequence context
  for auth drain/provider failures, including a final settled-state record.
  Keep payloads out of logs. Late rejected mutations must remain recoverable.
- Review a narrowly scoped operator recovery method only after those proofs;
  never make marker deletion or automatic retries the recovery mechanism.
These changes are not implemented or deployed in this alert correction.

Resuming the original IPv4 rollout
---------------------------------
The existing docs/bridge-ipv4-deployment.txt remains the execution procedure.
Its original approval covers exact commit 69bedb4, not this later UI commit.
Do not substitute a different artifact or skip readiness/journal/drain gates.
After session recovery is proven, repeat preflight from scratch, then follow
maintenance -> ngrok stop -> bridge drain/stop -> inbound drain -> API stop ->
offline validation -> approved release activation -> readiness -> reopen ingress.
Require eight owned IPv4 connections, TLS validation and successful heartbeat
responses, then staff acceptance, at least 60 minutes of attended monitoring
and a 24-hour comparison. None of those deployment verifications is claimed here.
