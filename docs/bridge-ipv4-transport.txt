Bridge-only IPv4 WebSocket transport
===================================
Scope: local implementation and focused mock verification, commit and PR.
No DEV or production access, deployment, live sessions or network changes.

Configuration and behavior
--------------------------
WHATSAPP_WS_IP_FAMILY=0 (or unset/empty): preserve the existing Baileys/ws
transport and Node address selection. No custom agent is supplied.
WHATSAPP_WS_IP_FAMILY=4: a private HTTPS agent restricts the bridge's WhatsApp
WebSocket DNS/TCP connections to IPv4, with automatic family fallback disabled.
Any other value fails configuration validation before bridge data is opened.

The agent is passed through Baileys' WebSocket-only `agent` option for every
identity and every replacement connection. No fetchAgent, DNS global, default
agent, server routing, media transport or callback transport is changed. The
provider's hostname remains in the URL; Node resolves it normally. No endpoint
IP is pinned. Certificate validation, hostname verification and hostname SNI
remain enabled. IPv4 connection failures enter existing visible transport-error
diagnostics and bounded reconnect handling; there is no fallback to IPv6.

Independent upgraded sockets leave the HTTP agent pool. Existing physical-close
and auth/event-drain barriers still govern replacement. Shutdown retires the
agent only after existing bridge drains. No change to heartbeat deadlines,
backoff, authentication, journal/checkpoint formats, delivery ordering, dedup,
uncertain-message handling, media limits, forwarding or frontend behavior.

Why this option, and what it does not prove
-----------------------------------------
Post-PR #81 production evidence strongly supports an intermittent IPv6 TCP
progress failure: raw receive and decoded receive both stopped, with unacked
bytes and retransmissions. This avoids that suspected path; it does not identify
whether the VPS, transit network or remote edge caused it, or guarantee that
IPv4 cannot fail. Compare timeout rates per connection-hour and recovery time
after activation, including endpoint/generation changes, rather than counts
alone. Do not infer a permanent cure from the local mock results.

Additional passive diagnostics
------------------------------
- Restricted bridge status/logs: configured_ip_family, existing actual remote
  IP/family/ports, TLS authorization, generation and receive/heartbeat timing.
- Fixed underlying socket error codes, end/close timestamps and close had_error.
  Observe before ws consumes errors/clears endpoints; remove only our listeners.
  No error message, stack, customer payload, close reason or secret is logged.
  No socket data listener, read, probe, packet capture or transport action added.
- Existing bounded ss collector: optional TCP bytes_received/bytes_acked/
  bytes_sent, inbound segments/data segments, unacked segments, time since
  receive/ACK, advertised send window and sample start/completion timestamps,
  in addition to retransmissions, RTT/RTO and queues.
- Export support_bridge_configured_ip_family, support_bridge_transport_family,
  support_bridge_transport_tls_authorized and support_bridge_tcp_* gauges.
  Prometheus retains hashed identity labels; endpoints/errors are not labels.

TCP ACKs are transport evidence, NOT WhatsApp message acknowledgment. Compare
kernel deltas only inside the same connection generation. Sampling is separate
from bridge status and may miss short failures. Unavailable counters remain
unknown, not zero; check tcp_sample_up and collector freshness. No new scrape
cadence, service permissions or alert policy is required by this change.

Results: 5 TLS/transport-option checks, 14 diagnostics/heartbeat checks,
6 selected ownership/delivery regressions and 10 Python collector checks pass
(35 total). The default-mode fixture was corrected to mock ws' actual direct
TLS path, then that affected check passed. Tests establish:
- Eight independent real loopback TLS/WebSockets via the installed Baileys
  adapter; successful echo, IPv4 peer family and hostname SNI; one socket closes
  without closing the others; its replacement uses IPv4.
- Untrusted certificate and wrong hostname rejected; strict IPv4 fails visibly
  even when the same port has a reachable IPv6-only listener.
- Unset/0 default keeps address selection unconfigured and permits mock IPv6;
  no process-global agent, resolver or address-family setting changes.
- Eight mocked identities retain duplicate-connect guards; renewal waits for
  actual physical closure; old-generation diagnostics are ignored; pending
  uncertain records/outbox remain unchanged and no provider send is replayed.
- Existing heartbeat accounting/failed-transport grace, terminal-failure retry
  suppression, passive diagnostics cleanup, metric privacy and optional TCP
  fields retain their safeguards.

Rollback (requires an approved graceful restart)
-----------------------------------------------
If IPv4 cannot reach WhatsApp or regressions occur, preserve the new authoritative
data and inspect the bounded error diagnostics. Set the same private environment
value to WHATSAPP_WS_IP_FAMILY=0 and perform the approved graceful bridge restart
with normal drain/physical-close gates. Explicit 0 avoids an unexpected fallback
value from .env. Verify 8/8 restored and staff acceptance again. The setting-only
rollback retains diagnostic and recovery code; it changes no host-wide routing.
If code rollback is necessary, use the approved prior immutable release with its
matching collector while retaining current persistent state; never restore old
auth, journals or messages over current state. Stop if ownership or drain gates
fail; do not kill a healthy owner to force replacement.
