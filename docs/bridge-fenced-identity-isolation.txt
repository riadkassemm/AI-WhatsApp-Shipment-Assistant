Root cause and new lifecycle contract
------------------------------------
Previously closeOnce drained all auth facades and then closed all owned
journals. auth.drain -> JournalStore.flush rejects a failed auth store, even
after all promises settle. Global readiness treated every failed auth store
as a service-wide failure. Normal JournalStore.load could repair journal tails
or remove checkpoint temporaries BEFORE noticing an authentication fence.

The states exposed per identity are active, gracefully_retired,
fenced_unresolved, and fenced_retained. Retention is NOT recovery:
- A held data-directory lock is required, including after every async read.
- A live owner must already be retired, have a confirmed closed transport and
  released subscriptions, no provider/key/credential/journal/health/checkpoint
  work, and a durable final evidence revision matching its actual in-memory
  operation outcomes and uncertain credentials. Retention calls no end/drain.
- All historical intent IDs must have completed/rejected wrapper outcomes;
  provider outcomes may be completed/rejected/not_started, never unresolved.
  Changed credentials/keys may remain uncertain: they are retained, not applied.
- Read-only replay must validate the auth AND message-state journals, with no
  incomplete tail. All auth/state files, markers and checkpoint leftovers are
  privately fingerprinted before/after inspection and again before closure.
- A failed-store facade is sealed in memory. No failed auth flush, commit,
  compaction, marker clearing, credential comparison output or journal repair.
  The ordinary JournalStore.close/flush behavior remains strict.
- Fenced identity callbacks stay in the durable outbox; its message recovery,
  upload, reconnect, reset and removal paths cannot write or submit anything.
  Historical local media can still be read. Uncertain deliveries are not resent.
- Six healthy identities use the normal auth/message/callback drain. Physical
  transport closure is awaited before the directory ownership lock is released.
- A preflight failure leaves the healthy sockets and HTTP listener running.
  Missing final evidence on a cold start blocks all provider activation; the
  authenticated status endpoint remains available. No missing proof is ignored.

Readiness excludes ONLY the auth STORE_UNAVAILABLE issue for a positively
retained identity. Raw storage failure and per-identity recovery requirements
remain visible. Shared outbox/state failure, capacity, stale monitoring and
unproven retention still block readiness. Operators must see the fenced warning.

Rollback — preserve new authoritative state
--------------------------------------------
Do not restore old auth/Redis/DB snapshots over new writes. An old binary such
as b5f8e35 cannot safely consume retained-fence lifecycle state; rolling its
code back would reintroduce the shutdown/readiness defect. Keep it archived,
but do not treat it as an automatically runnable rollback.

The smallest transport rollback is the SAME reviewed isolation-capable code
with WHATSAPP_WS_IP_FAMILY unset/0. Obtain separate approval; rerun preflight,
maintenance, no-SIGKILL, clean-stop and queue gates. Preserve fresh evidence,
atomically restore only the previous IP-family setting in app.env, then start
API -> bridge and validate six eligible + fenced Beirut before ingress/ngrok.
Do not copy the entire previous environment over unrelated current settings.

If an isolation/code fault appears after writes begin, close ingress only as
approved, preserve current state, and request a separately reviewed compatible
rollback/hotfix. No fence clearing, forced termination, selective journal
rewind, or uncertain-message replay is an acceptable rollback shortcut.
